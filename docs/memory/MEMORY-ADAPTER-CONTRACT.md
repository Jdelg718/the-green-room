# Memory Adapter Contract 1.0

This is the normative, implementation-independent contract selected by [ADR 0002](../adr/0002-self-hosted-memory-adapters.md). The key words **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are normative.

## 1. Trust and privacy boundary

```text
model -> proposal (untrusted data)
             |
             v
harness policy + schema + provenance validation
             |
             v
committed operation -> selected user-owned adapter
```

The free harness is software the user runs. The Green Room project hosts no conversations, room state, model traffic, credentials, or memory. An adapter receives only one scoped operation at a time, never a model prompt, system instructions, secrets, or an entire vault. No telemetry leaves the user's deployment by default.

The harness, not a model or adapter, decides whether a proposal is retained. A proposal is plain data with no adapter credentials or callable operation. The harness MUST:

1. enforce room/persona scope and user policy;
2. reject unsupported fields and instruction-like attempts to alter runtime policy;
3. verify every cited event exists in the same room and is visible to the proposing scope;
4. enforce text, evidence, item, and classification limits;
5. show/review proposals when policy requires it;
6. construct the committed record, revision, provenance, idempotency key, and precondition.

Adapter output is untrusted data. The harness MUST schema-validate it, treat returned text as quoted memory data, delimit it from control instructions in any model context, and never interpret returned URLs, Markdown, HTML, tool syntax, or role labels as executable instructions.

## 2. Version and negotiation

The media type is `application/vnd.greenroom.memory+json;version=1.0`. Every request and response has exact `contract_version: "1.0"`; numeric `1` or compatible-looking versions are invalid.

`health` MUST be callable without room data and returns:

- adapter implementation name/version;
- supported contract versions (including exact `1.0`);
- capability booleans: `append_events`, `records`, `retrieve`, `export_import`, `migration`, `physical_erase`;
- effective hard maxima for request bytes, response bytes, operations, records, evidence IDs, text bytes, and timeout;
- durability (`durable`, `best_effort`, or `read_only`) and degradation reasons;
- schema/storage version and whether migration is required.

Negotiation chooses the highest exact version present in both sets. There is no minor-version inference. Unknown operations, fields, enum values, or versions fail closed with `unsupported`.

## 3. Identifiers, time, and ordering

IDs are lowercase UUIDv7 strings. Implementations MUST reject noncanonical spelling. IDs are generated by the harness except adapter-generated `commit_id` and `export_id`.

- `event_id`: immutable identity of one authoritative room event.
- `record_id`: stable identity of one logical derived memory.
- `revision_id`: immutable identity of one committed revision.
- `operation_id`: one request instance used for audit.
- `idempotency_key`: caller-generated UUIDv7 identifying the semantic write attempt.
- `commit_id`: adapter-generated UUIDv7 identifying a successful atomic commit.

Timestamps are UTC RFC 3339 strings with exactly three fractional digits and terminal `Z`, such as `2026-08-30T16:00:00.000Z`. They are descriptive, not ordering authorities. Per-room `event_sequence` is an unsigned integer allocated atomically by the adapter. Committed derived revisions use per-record `revision` integers starting at 1. Tie-breaking for retrieval is specified in section 9.

An event's immutable identity covers canonical JCS bytes of all event fields except transport envelope. JCS means RFC 8785 exactly, including ECMAScript number serialization and UTF-16 property-name ordering; ordinary language-native `sort_keys` JSON is not conformant. Adapters MUST reject values RFC 8785 cannot represent (including non-finite numbers and lone surrogates). `event_id` is not content-addressed; the immutable `content_digest` is `sha256:<64 lowercase hex>` over those JCS bytes with `content_digest` omitted. Reusing an event ID with different bytes is `id_collision`.

## 4. Record model

The JSON Schemas in [`schemas/`](schemas/) are normative. All objects use `additionalProperties: false`.

### 4.1 Authoritative room event

An event contains `event_id`, `room_id`, `event_sequence`, `occurred_at`, `kind`, `actor_id`, `visibility`, `payload`, and `content_digest`. Events are append-only and authoritative. An adapter MUST NOT summarize, reinterpret, or mutate event payloads.

`append_events` accepts 1–100 events for exactly one room, at most 1 MiB total and 256 KiB per event. The adapter atomically assigns a contiguous sequence range unless the caller supplies already assigned events during verified import. The entire batch succeeds or none does.

### 4.2 Derived memories

Kinds are:

- `room`: bounded room facts/preferences applying to all participants;
- `persona`: memory scoped to one persona's future behavior;
- `relationship`: directional memory from `source_persona_id` toward `target_persona_id`; reverse direction is a different record;
- `episode`: bounded summary of an event interval.

A derived revision contains stable `record_id`, immutable `revision_id`, monotonic `revision`, `room_id`, `kind`, exact scope, `body`, `status`, `provenance`, `created_at`, and `created_by`.

`body` is UTF-8 text, at most 16 KiB after UTF-8 encoding. JSON Schema `maxLength` is only an early code-point bound; every adapter and the harness MUST perform the normative encoded-byte check before allocation, digesting, or persistence. It is historical data, not an instruction channel. Relationship bodies SHOULD describe observable changes and MUST NOT claim symmetric state. Episode summaries MUST cite at least one event and include `event_range` whose endpoints exist.

### 4.3 Provenance

Every active derived revision MUST contain:

- nonempty, sorted, unique `source_event_ids` from the same room;
- `derivation.kind`: `model_proposal`, `human_edit`, `import`, `compaction`, or `correction`;
- `derivation.producer`: local model/provider profile identifier or `human` (never a credential);
- optional `proposal_id` and `policy_version`;
- `created_at` and `created_by` (`harness`, `user`, or `migration`);
- for compaction, sorted `source_revision_ids` and `compaction_level`.

A retrieval result repeats the selected revision's provenance. Similarity scores never become provenance.

## 5. Operations

The closed operation set is:

| Operation | Mutates | Required behavior |
| --- | --- | --- |
| `health` | no | Version/capability/bounds only; no private records. |
| `append_events` | yes | Atomic immutable append. |
| `commit_records` | yes | Atomic create/correct/compact/tombstone batch. |
| `get_events` | no | Ordered bounded event page. |
| `get_records` | no | Filtered bounded record page. |
| `retrieve` | no | Relevant active records under caller budgets. |
| `export` | no | Deterministic portable bundle. |
| `import` | yes | Validate/dry-run/atomic commit bundle. |
| `migrate` | yes | Explicit resumable schema migration. |
| `reset` | yes | Tombstone a room-derived view; optional event erase is separate. |
| `erase` | yes | Explicit physical purge where supported. |

No operation accepts a command, script, module name, executable path, callback URL, arbitrary SQL, or plugin identifier.

Every operation has a standalone, closed request and response schema named `<operation>-request.schema.json` and `<operation>-response.schema.json` in [`schemas/`](schemas/), with underscores rendered as hyphens. Each response schema accepts exactly either its operation-specific `status: "ok"` outcome or its operation-specific `status: "error"` envelope. [`error.schema.json`](schemas/error.schema.json) is the closed cross-operation error union. All schemas reject unknown fields and pin `contract_version`, `operation`, and outcome shape; dispatch MUST validate against the schema selected by the exact operation name and MUST NOT probe compatible shapes. The normative examples in [`operation-envelopes.json`](fixtures/memory-adapter/valid/operation-envelopes.json) cover all eleven pairs.

The six mutators (`append_events`, `commit_records`, `import`, `migrate`, `reset`, and `erase`) require `idempotency_key` and `request_digest`. `append_events` and `commit_records` carry optional room-generation CAS, each record write carries `if_revision`, import carries per-room generations, reset carries room generation, migration binds an approved backup digest, and erase binds a fresh confirmation object. Their successful responses identify the durable commit and exact outcome. Read requests carry explicit snapshot/page/budget fields, and read responses carry snapshot, counts, bytes, truncation, and cursor state where applicable.

## 6. Idempotency, transactions, CAS, and conflicts

Every mutating request carries an `idempotency_key` and `request_digest`. `request_digest` is SHA-256 over JCS canonical request-envelope data with only `idempotency_key`, `request_digest`, authentication, and transport fields omitted; the contract version, operation ID/name, payload, CAS preconditions, and confirmation fields remain covered. The adapter retains the key, digest, and complete response outcome for at least 30 days or until the enclosing room is physically erased.

- First valid use executes exactly once and stores the outcome.
- Same key and same digest returns the original status/body and `commit_id` without re-execution.
- Same key and different digest returns `idempotency_mismatch`.
- A transport timeout is indeterminate; the caller retries the identical request/key.

Writes are atomic at request scope. `commit_records` has a precondition per logical record:

- create: `if_revision: 0`;
- update/tombstone: `if_revision: N` matching the active revision;
- optional room-wide `if_room_generation` prevents writes across reset/import.

A failed precondition returns `conflict`, current revision/generation metadata, and commits nothing. The harness MAY re-read, re-evaluate policy, and retry with a new idempotency key. Blind last-writer-wins is forbidden.

Appending an existing `event_id` with identical canonical bytes is a successful replay. Different bytes are `id_collision`. Import duplicates are compared by immutable IDs and digests; no timestamp-based winner is allowed.

## 7. Correction, tombstone, forget, reset, and erase

**Correction** appends a new active revision with `supersedes_revision_id`, `derivation.kind: correction`, and the original plus any new evidence. The old revision remains inspectable and is excluded from default retrieval.

**Forget record** appends a `status: tombstoned` revision with an optional user-visible reason. Tombstones have no body, remain in lineage, and exclude all earlier revisions from retrieval.

**Reset** increments `room_generation` and atomically appends room-scope tombstones for active derived records selected by scope. By default it preserves events so memories can be rebuilt. The response states exact counts.

**Erase** is a separate destructive operation requiring a fresh user confirmation token bound to room, requested scope, and expiry. `derived_only` physically removes derived revisions after an export opportunity. `all_room_data` removes event log, derived records, indexes, idempotency entries, temporary files, and adapter-owned backups for that room where supported. The adapter reports unsupported or delayed external copies; it MUST NOT claim to erase user-managed sync/version history or independent backups.

After erase, the adapter writes no tombstone containing private content. It MAY retain a content-free audit marker (`room_id`, erase time, scope) only if the user opted into local audit retention.

## 8. Compaction and lineage

Compaction creates a new revision; it never rewrites source events or source revisions. A compaction revision MUST list all direct `source_revision_ids`, all transitive unique `source_event_ids`, `compaction_level = max(source levels)+1`, and a deterministic `lineage_digest` over sorted source revision IDs. Cycles, missing sources, mixed rooms, tombstoned sources, and more than 256 direct sources fail validation.

An implementation MUST support lineage inspection and rebuilding derived state from events. Compaction may reduce retrieval candidates but cannot make its summary authoritative over cited events.

## 9. Retrieval

`retrieve` is read-only and contains:

- one `room_id` and optional persona/directional relationship scope;
- a query of at most 4 KiB after UTF-8 encoding (enforced semantically in addition to the schema code-point bound);
- allowed kinds and classifications;
- `as_of_event_sequence` for stable snapshots;
- budgets: `max_items` (1–50), `max_total_bytes` (1–131072), `max_item_bytes` (1–16384), and `timeout_ms` (10–2000).

The adapter MUST apply all budgets and return partial results only with `truncated: true` and a machine-readable reason. It MUST NOT exceed a byte or item bound to include one more result. `elapsed_ms`, `items_returned`, and `bytes_returned` are required.

Candidates are active, not tombstoned, within scope/classification, and supported by events not later than the snapshot. Ranking MAY combine lexical, recency, and local vector scores, but returns an explainable `match` object. Deterministic tie order is descending normalized score, descending newest supporting `event_sequence`, then ascending `record_id` bytes. Scores do not assert truth.

Returned text is verbatim committed memory, not synthesized at retrieval time. Each item includes record/revision IDs, kind/scope, body, provenance, and match reason. Retrieval has no write side effect.

## 10. Enumeration and pagination

`get_events` orders by `(event_sequence, event_id)`. `get_records` orders by `(record_id, revision)`; `include_history: true` returns every superseded and tombstoned revision, while `false` returns only each record's current revision. Opaque cursors bind adapter instance, filters, snapshot generation, and last key; they expire after at least 10 minutes. A cursor with changed filters or generation returns `cursor_invalid`, never an inconsistent page. Page count, byte limit, and timeout are mandatory.

## 11. Deterministic export and import

An export is a UTF-8 ZIP with fixed paths, no encryption, no links, no duplicate names, and these entries:

```text
manifest.json
rooms/<room-id>/events.ndjson
rooms/<room-id>/records.ndjson
```

Entries are lexicographically ordered, timestamps in ZIP headers are `1980-01-01T00:00:00`, permissions are normalized to `0644`, and compression is DEFLATE level 6. JSON lines are RFC 8785 JCS plus LF. Events sort by sequence/ID; revisions sort by record ID/revision. `manifest.json` conforms to [`export-manifest.schema.json`](schemas/export-manifest.schema.json) and lists contract/storage version, export scope, aggregate room/event/revision/active/tombstone counts, and SHA-256, byte length, and item count for every other entry.

Export identity and time are snapshot-derived, never wall-clock values generated for an export attempt. First form `snapshot_descriptor` as JCS of the exact sorted room IDs, each selected room generation and `as_of_event_sequence`, scope, classifications, contract version, and storage version. `snapshot_digest` is SHA-256 of those bytes. `export_id` is a deterministic lowercase UUIDv7: encode `created_at` Unix milliseconds in the first 48 bits, fill the remaining payload bits in order from `SHA-256("greenroom-export-v1" || snapshot_digest-bytes)`, and set the version and variant bits. `created_at` is the greatest `occurred_at` or record `created_at` included in that snapshot, or `1970-01-01T00:00:00.000Z` for an empty selected snapshot. Thus retrying or re-exporting the same snapshot produces the same manifest and ZIP bytes. Any change to selected snapshot state changes its descriptor. Credentials, endpoint URLs, adapter auth, model API keys, local absolute paths, and nonselected classifications are excluded. Persona-pack export is separate and never includes memories unless explicitly selected.

Import rejects absolute/traversal/backslash/control-character paths, links/reparse entries, duplicate or case-fold-colliding names, unsupported compression, encrypted entries, extra entries, digest/count mismatch, uncompressed size over 64 MiB, more than 100,000 records, compression ratio over 100:1, schema errors, and cross-room references. `dry_run: true` returns a plan without writes. Commit is atomic and uses ID/digest/CAS semantics. Import never restores credentials.

## 12. Migration

Storage schemas are integer versions scoped to an adapter implementation; contract version is independent. The adapter MUST open a newer unknown storage version read-only. Migration requires explicit user approval after a local backup/export, uses a lock and migration journal, is resumable/idempotent by step ID, verifies counts/digests, and retains the pre-migration backup until the user accepts verification. Downgrade is export-to-supported-format plus new-store import, not in-place mutation.

## 13. Errors

Responses use one of: `invalid_request`, `unsupported`, `not_found`, `conflict`, `id_collision`, `idempotency_mismatch`, `budget_exceeded`, `timeout`, `unavailable`, `read_only`, `migration_required`, `corrupt_store`, `unsafe_path`, `unsafe_endpoint`, `auth_failed`, or `internal_error`.

Errors contain a stable code, safe message, retryability, and operation ID. They MUST NOT include secrets, full private record bodies, absolute vault paths, stack traces, SQL, or HTTP authorization material. An adapter failure never causes fallback to a different backend without user approval.

## 14. Built-in local reference mapping

The built-in adapter stores everything on the user's machine:

- SQLite in WAL mode with foreign keys and `synchronous=FULL` by default;
- separate immutable `events`, versioned `records`, `record_evidence`, `idempotency`, `room_generation`, and `migration_journal` tables;
- FTS/vector indexes are disposable derivatives and rebuilt from committed rows;
- database and export directory permissions are user-only where the OS supports it;
- secrets are absent from the database;
- a transaction implements every atomic request;
- `PRAGMA integrity_check`, foreign-key check, record/evidence counts, and an export/import round trip form backup verification.

A network filesystem that cannot support SQLite locking MUST be rejected or opened read-only; it is not silently downgraded.

## 15. Conformance

An adapter is conformant only if it passes [the common suite](CONFORMANCE.md), advertises only proven capabilities, and documents any weaker durability. Schema validity alone is insufficient.
