# Obsidian backend: exact managed format and lifecycle

This is the normative filesystem projection for Memory Adapter Contract `1.0`. The adapter works on files; Obsidian does not need to be installed or running. An Obsidian vault is a local filesystem folder, and Obsidian properties are YAML at the beginning of a Markdown file (sources 1 and 2).

## Ownership boundary

During setup the user selects a vault root and accepts exactly one managed child named `Green Room`. The adapter owns only descendants of that child. It MUST NOT read, enumerate, watch, index, modify, rename, or delete siblings, the vault's `.obsidian/` configuration, or any user note outside `Green Room/`.

Within `Green Room/`, the adapter owns only paths listed in `state/managed-files.json`. `README.md` contains a clearly marked generated block and a user-notes block. The adapter never changes bytes inside the user-notes block. Unrecognized files are user-owned and ignored. A generated note's body has a generated section and a user annotation section; user bytes are preserved exactly unless the user explicitly imports an edit.

The wizard shows this tree before creation:

```text
Green Room/
├── README.md
├── rooms/
│   └── <room-id>/
│       ├── room.md
│       ├── events/
│       │   └── YYYY-MM.ndjson
│       ├── episodes/<record-id>.md
│       ├── people/<persona-id>/<record-id>.md
│       ├── relationships/<source-id>--<target-id>/<record-id>.md
│       └── memories/<record-id>.md
├── state/
│   ├── adapter.json
│   ├── managed-files.json
│   ├── operations.ndjson
│   ├── quarantine/
│   └── recovery/
└── .locks/
```

IDs are validated before path interpolation. A room/persona/record ID is a lowercase UUIDv7, never a display name. Relationship directions are explicit. All relative paths use `/` in manifests and are case-sensitive logical names even on case-insensitive filesystems.

## Exact bytes

All managed text is UTF-8 without BOM, NFC-normalized where text is generated by the harness, uses LF line endings, and ends in exactly one LF. JSON is RFC 8785 JCS. An NDJSON line is one JCS object followed by LF. No tabs or trailing spaces are generated.

A Markdown note has this exact shape and frontmatter key order:

```markdown
---
greenroom_schema: "1.0"
greenroom_kind: "episode"
room_id: "018f0f6e-7b6a-7c10-8af1-7f4c620b93c1"
record_id: "018f0f70-3905-7bc0-9d40-4c85432a4c17"
revision_id: "018f0f70-49cf-7a96-86f5-12dbcb88ef11"
revision: 1
status: "active"
created_at: "2026-08-30T16:04:00.000Z"
source_event_ids:
  - "018f0f6f-a3d2-7d09-bd19-d6325d4bc77a"
body_sha256: "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
generated_sha256: "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
---

# Episode

<!-- greenroom:generated:start -->
The group agreed to compare two approaches before deciding.

## Provenance

- Event `018f0f6f-a3d2-7d09-bd19-d6325d4bc77a`
<!-- greenroom:generated:end -->

<!-- greenroom:user-notes:start -->
<!-- Your notes here are preserved. Use Green Room to adopt them as memory. -->
<!-- greenroom:user-notes:end -->
```

YAML values are always quoted strings except `revision`, which is a decimal integer, and `source_event_ids`, which is a sorted block list of quoted strings. No anchors, aliases, tags, flow collections, multiline scalars, duplicate keys, or unknown properties are emitted or accepted as managed metadata. Obsidian properties support text, lists, numbers, dates, and related atomic types, but Markdown inside properties is intentionally unsupported; therefore prose remains in the body (source 2).

`body_sha256` covers the UTF-8 bytes of the committed body only. `generated_sha256` covers bytes from immediately after the generated-start marker's LF through immediately before the generated-end marker. The fixture tree under [`fixtures/obsidian-vault`](fixtures/obsidian-vault/) is byte normative; `expected-bytes.json` contains every managed path, byte count, and SHA-256.

`room.md` and `README.md` follow the same marker rules. `state/*.json` and `.locks/` are hidden from normal human use but remain inside the disclosed subtree. State files are canonical JSON plus LF.

## Event segments

`events/YYYY-MM.ndjson` is append-only. The month is derived from `occurred_at` UTC. Before append, the adapter holds the room lock and verifies the file's saved byte length and SHA-256 from `managed-files.json`. It writes complete lines with one OS append handle, flushes, syncs, then updates the manifest atomically. A torn final line is never treated as an event. Recovery truncates only bytes after the last manifest-confirmed offset and quarantines unexpected complete lines for reconciliation.

Events are never edited from Obsidian. External event-file changes mark the room `needs_reconciliation` and block all writes. The user may restore expected bytes, quarantine foreign lines, or import valid new events through the harness. The adapter never silently chooses a winner.

## Path and link defense

Lexical prefix checks alone are insufficient. For every open, create, rename, unlink, scan, or lock operation, the adapter MUST:

1. reject absolute paths, `..`, `.`, empty segments, backslashes, NUL/control characters, Windows drive/UNC/device syntax, trailing dot/space segments, reserved Windows names, alternate data stream `:`, overlong names, and case-fold/NFC collisions;
2. open the already-approved vault and managed root as directory handles and resolve every component relative to those handles;
3. reject symbolic links, hard links where link count is unexpected, mount points, junctions, and all Windows reparse points in every existing component and target;
4. create with no-follow/exclusive semantics and restrictive permissions;
5. compare the final opened object's filesystem identity and canonical parent chain to the approved root immediately before mutation;
6. repeat containment/link checks after acquiring the lock to close check/use races.

On POSIX, use descriptor-relative operations such as `openat`/`renameat`, `O_NOFOLLOW`, and same-filesystem temporary files. On Windows, open reparse points themselves for inspection and reject them; Microsoft documents that reparse points can alter ordinary file-operation behavior and require special handling (source 3). If the platform cannot supply safe primitives, the adapter MUST refuse writable mode.

## Locks and concurrent writers

The writer takes `.locks/adapter.lock` with an OS advisory exclusive lock and records only process start nonce and expiry (no secrets). It then takes the room lock in lexicographic room-ID order. Locks are held through file sync, manifest replacement, and operation journal commit. Readers take a shared adapter lock or read from a manifest-confirmed snapshot.

A lock file's age alone never proves abandonment. Recovery verifies the recorded process nonce is not live, acquires the OS lock, and then takes ownership. Default wait is 2 seconds; timeout returns `conflict` and performs no write. Network/cloud placeholder filesystems or locks that fail a setup contention probe are read-only/unsupported.

Each mutation uses CAS against `generated_sha256`, record revision, room generation, and the manifest generation. Obsidian and sync tools are concurrent external writers; there is no last-writer-wins path.

## Atomic write and recovery protocol

For a mutable generated file:

1. acquire locks and revalidate path/manifest/CAS;
2. render complete deterministic bytes in memory within limits;
3. create `state/recovery/<operation-id>/<basename>.tmp` exclusively on the same filesystem;
4. write all bytes, set restrictive permissions, flush, and sync the file;
5. journal `prepared` with old/new digests and target relative path, then sync journal;
6. atomically replace the target (POSIX same-filesystem rename; Windows `ReplaceFileW` when replacing) and sync the containing directory where supported;
7. atomically replace `managed-files.json` with incremented generation;
8. journal `committed`; sync; remove temporary/backup files.

POSIX rename atomically replaces an existing destination, while Microsoft's `ReplaceFile` combines replacement and preserves selected original attributes; its documented partial-failure states must be handled during recovery (sources 4 and 5). Atomic visibility is not assumed to equal power-loss durability. `health.durability` reports whether file and directory sync are supported.

At startup, recovery holds the exclusive adapter lock and replays `operations.ndjson`:

- no `prepared`: remove unreferenced temp files after path validation;
- prepared, target old digest: retry replacement;
- prepared, target new digest: finish manifest and commit journal;
- any other digest or missing source: quarantine operation, mark store read-only, require user decision;
- committed: cleanup only.

Never delete a questionable copy during recovery. Quarantine names are operation IDs, not user-controlled originals.

## External edits and sync conflicts

At scan/open and before every write, compare managed path, bytes, and revision against the manifest.

- Only user-notes bytes changed and markers/frontmatter/generated digest remain valid: preserve bytes; no memory semantic change.
- Generated body changed with valid metadata: create a visible reconciliation proposal. If the user adopts it, the harness validates it and commits a new `human_edit` revision; otherwise restore generated bytes while preserving annotations.
- Frontmatter, markers, path, event log, state file, or unsupported bytes changed: quarantine a copy, mark conflict, and stop writes for that room.
- Missing generated file: offer restore from committed state or forget; never infer deletion intent.
- Duplicate/conflict filename: ignore as untrusted until the user chooses a valid lineage.

Obsidian Sync may merge conflicting Markdown, may produce duplicate/formatting problems, and uses last-modified-wins for other file types; it can alternatively create a separately named conflict file (source 6). Consequently, the adapter treats both merged managed notes and any `*(Conflicted copy ...).md`/provider-specific conflict artifact as conflicts, never as automatic commits. JSON/NDJSON are not merged.

The adapter does not configure Obsidian Sync, Syncthing, iCloud, Git, or any cloud service. Sync is the user's responsibility and is not a backup. Obsidian's own guidance distinguishes sync from backup and recommends a separate one-way backup (source 7).

## Backup, disconnect, and erase

**Backup:** pause writes, lock, recover, verify manifests and event lines, create a deterministic contract export outside the vault, and optionally copy the entire `Green Room/` subtree to a user-selected backup. Report exact counts/digests. Never place credentials in either artifact.

**Disconnect:** flush and verify, release locks, remove only the local adapter configuration/secret reference, and leave the `Green Room/` subtree untouched. Show how to reconnect. Disconnect is not deletion.

**Erase:** require scoped confirmation. First offer export. Delete only manifest-listed adapter-owned files using descriptor-relative no-follow operations, bottom-up; preserve unknown/user files and user annotations by default. If unknown files remain, leave the subtree and report them. External sync histories and independent backups are outside adapter control and must be disclosed, not claimed erased.
